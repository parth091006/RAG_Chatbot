# Advanced RAG Research Assistant

## 1. Executive Summary

This project is an Advanced Retrieval-Augmented Generation (RAG) Research Assistant built for research-paper analysis. It allows users to upload PDFs, ask questions about the documents, compare multiple sources, and receive grounded answers with citations.

The system is designed to go beyond a simple "chat with PDF" workflow. It includes:

- PDF ingestion and parsing
- Text and metadata extraction
- Intelligent chunking
- Embedding generation
- Dense vector search
- Sparse keyword retrieval
- Hybrid retrieval
- Reranking
- Citation tracking
- Multi-document QA
- Cross-document comparison
- Retrieval and generation evaluation
- Tracing and observability
- REST API exposure
- Dockerized deployment

The core idea is to combine a model's generative ability with a retrieval system that supplies relevant, verifiable evidence from external documents. In RAG, the model is not expected to rely only on its pretrained memory; it is grounded in retrieved context.

The end goal is to build, evaluate, expose, and containerize a complete RAG system:

Ingestion → chunking → embeddings → retrieval → generation → evaluation/tracing → API → Docker

## 2. Project Goal

### Project title
Advanced RAG Research Assistant

### Primary objective
Build an application that can answer questions using research papers while providing evidence for every answer.

### Example scenario
A user uploads:

- attention_is_all_you_need.pdf
- bert.pdf
- gpt2.pdf
- llama.pdf

Then asks:

> Compare the training objectives of BERT, GPT-2, and LLaMA.

The system should follow this pipeline:

Question → query analysis → hybrid retrieval → candidate documents → reranking → relevant evidence → LLM → comparison → citations

The answer should be grounded in the retrieved sources, not just the model's prior knowledge.

Example output:

| Aspect | BERT | GPT-2 | LLaMA |
| --- | --- | --- | --- |
| Architecture | Encoder | Decoder | Decoder |
| Objective | Masked LM | Autoregressive LM | Autoregressive LM |
| Evidence | BERT p. X | GPT-2 p. X | LLaMA p. X |

## 4. Final System Architecture

The project architecture can be visualized as:

```text
PDF Upload
   ↓
PDF Processing (text + metadata)
   ↓
Chunking
   ↓
Embeddings
   ↓
Vector Database
   ↓
User Question
   ↓
Query Processing
   ├── Dense Retrieval
   └── BM25 / Sparse Retrieval
   ↓
Hybrid Fusion
   ↓
Reranker
   ↓
Top-K Evidence
   ↓
LLM (answer generation)
   ↓
Answer + Sources
   ├── Tracing
   └── Evaluation
   ↓
FastAPI
   ↓
Docker
```

The main processing flow is:

1. Documents are ingested and parsed.
2. Text is split into chunks.
3. Chunks are converted into embeddings.
4. The vector store stores the chunks and metadata.
5. The query is processed and matched against the index.
6. Dense and sparse retrieval results are combined.
7. Reranking selects the strongest evidence.
8. The LLM generates a grounded answer.
9. Citations, traces, and evaluation metrics are tracked.
10. The application is exposed through an API and containerized.

## 7. Information Retrieval Fundamentals

This is one of the most important areas for the project.

### Sparse retrieval
Keyword-based retrieval using methods such as:

- TF-IDF
- BM25

### Dense retrieval
Semantic retrieval where a query is embedded and matched against document embeddings.

### Hybrid retrieval
Combines both:

- dense retrieval
- sparse retrieval

This is useful because semantic search and keyword search each have different strengths.

Production RAG systems often rely on:

- metadata filtering
- hybrid search
- reranking
- chunk optimization

You should understand:

- vectors
- indexes
- similarity search
- metadata
- top-k retrieval
- filtering
- persistence

For a learning-focused version, FAISS is a great starting point because it exposes the fundamentals clearly.

Recommended learning progression:

FAISS → persistent vector store → production vector DB

Avoid jumping into a complex distributed vector database too early.

## 9. RAG Fundamentals

The difference between a plain LLM and a RAG system is essential:

### Plain LLM
Question → LLM → answer

### RAG
Question → retriever → relevant evidence → LLM → answer

In RAG, the model receives external knowledge as context before generating the answer.

### Version 1 — PDF ingestion
Goal: convert a PDF into structured document content.

Expected output:

```text
Document
├── page
├── text
└── metadata
```

Example internal representation:

```json
{
  "document_id": "doc_001",
  "filename": "attention.pdf",
  "page": 3,
  "text": "..."
}
```

Important metadata to keep:

- document_id
- document_name
- page_number
- chunk_id
- section
- source

### Version 2 — Chunking
Goal: split documents into manageable chunks.

Example chunk IDs:

- doc_001_page_1_chunk_1
- doc_001_page_1_chunk_2
- doc_001_page_2_chunk_1

Start with:

- 500–800 tokens per chunk
- 10–20% overlap

These are starting values, not final assumptions.

### Version 3 — Embeddings
Goal: convert each chunk into a vector.

Pipeline:

Chunk → embedding model → vector

Store:

- chunk_id
- embedding
- text
- metadata

### Version 4 — Vector retrieval
Goal: retrieve the most relevant chunks for a question.

Question → embedding → vector search → top-k chunks

### Version 5 — Basic RAG
Goal: connect the retriever to an LLM.

Question → retriever → relevant chunks → prompt → LLM → answer

Prompt instructions should require:

- answer using only the supplied context
- say when information is missing
- do not invent facts
- include citations

### Version 6 — Citations
Goal: make outputs traceable.

Each chunk should carry:

- document
- page
- chunk_id

Then answers can include references such as:

- [1] Attention Is All You Need — Page 3
- [2] Attention Is All You Need — Page 4

### Version 7 — Multi-document RAG
Goal: support more than one paper in the index.

Example question:

> What approaches to positional encoding are discussed across these papers?

### Version 8 — Metadata filtering
Add filters such as:

- document
- author
- year
- topic
- page
- section

This enables richer retrieval workflows.

### Version 9 — Hybrid retrieval
Add BM25 alongside dense search.

Pipeline:

Query → dense retrieval + BM25 → score fusion → candidates

This helps with both semantic and exact-term matching.

### Version 10 — Reranking
Use a second-stage reranker to reduce a large candidate pool down to the best few chunks before generation.

### Version 11 — Multi-document comparison
The system should compare multiple papers and structure the output clearly.

Example:

- Architecture
- Training objective
- Limitations
- Similarities and differences

### Version 12 — Evaluation
Treat evaluation as a core project goal, not an afterthought.

Use a dataset of questions, expected sources, and expected answers.

## 19. Prompt Architecture

Do not use one giant prompt for everything.

### QA prompt
Instructions should say:

- answer using only the supplied evidence
- say when information is insufficient
- do not invent information
- cite the evidence

### Comparison prompt
Instructions should say:

1. identify evidence for each document
2. state differences
3. avoid unsupported inference
4. attach citations

### No-answer behavior
If nothing relevant is found, the model should respond with a statement like:

> I couldn't find sufficient evidence in the provided documents to answer this question.

This prevents confident hallucination.

---

## 20. Citation Architecture

The system should not rely on the LLM to invent citations after the fact. Citation support should be built into the pipeline.

For each context item, use a deterministic identifier such as:

```text
[DOC1-P3-C2]
```

The backend maps this identifier back to:

- document name
- page number
- chunk

This provides a more reliable citation layer.

7. Ambiguous questions
8. Prompt injection inside uploaded PDFs

34. The Most Important Learning Principle
I want you to follow this rule throughout the project:
Every component must exist because you can explain the problem it solves.

For example:
Why embeddings?
Because keyword matching alone doesn't capture semantic similarity.
Why BM25?
Because exact terminology and identifiers can be important.
Why hybrid retrieval?
Because dense and sparse retrieval have complementary strengths.
Why reranking?
Because initial retrieval is optimized for recall/speed, while reranking can improve precision.
Why citations?
Because a research assistant needs provenance.
Why evaluation?
Because you need evidence that an architectural change actually improves the system.
Why tracing?
Because you need to know where failures and latency originate.
Why Docker?
Because the application should be reproducible outside your development machine.
If you can explain all of those, you won't just have built a RAG project—you'll understand RAG engineering.
